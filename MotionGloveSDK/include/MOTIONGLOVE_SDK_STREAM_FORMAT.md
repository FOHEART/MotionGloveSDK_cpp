# 网络数据流文本格式说明

本说明描述 SDK 通过 UDP 发出的「可读字符串数据流」的完整格式：整帧由哪些片段组成、
每个片段在哪些配置下出现、片段内可以出现哪些取值、以及每个取值代表什么含义。

- 生成实现：`src/stream/libH2StreamGenClass.cpp`（`genMotionGloveStream()` / `splitFrame()`）
- 对外声明：[libH2StreamGenClass.h](../../inc/stream/libH2StreamGenClass.h)
- 格式配置结构：[motionGloveStreamConfig.h](../../include/motionGloveStreamConfig.h)
- 发送实现：`src/network/h2NetworkMgr.cpp`（`TxStdStringMsg()`）
- 骨骼索引与名称：[motionGloveSDK_skeleton32Def.h](../../include/motionGloveSDK_skeleton32Def.h)、
  [motionGloveSDK_skeleton42Def.h](../../include/motionGloveSDK_skeleton42Def.h)
- 手势模板名：`src/gesture/gestureManager.cpp`

数据流是**纯 ASCII 文本**，一帧一行。发送端每个 UDP 报文携带一帧的一个「分包」，
分包之间没有二进制分隔符；CSV 录制把同一份文本按帧写成文件行。

---

## 1. 整帧模板

```
<ActorName> [time <时间> ][pos ][quat |euler <通道顺序> ][relative |global ][ges_l <左手势> ges_r <右手势> ][摇杆字段…]fn <帧号> [skeleton_32 |skeleton_42 |skeleton_openxr ],<骨骼数值串>
```

`[…]` 表示该片段只在对应配置打开时出现，顺序固定不可调换。

骨骼段数标记放在 **`fn <帧号>` 之后、分隔逗号之前**（即帧头的最后一个 token），**尚未实现**
（见 2.9 节）；现有帧一律按 `skeleton_32` 解析。放在这里是为了不破坏现有结构：
整帧第一个 token 仍然是 `<ActorName>`。

生成结束后会把**末尾那个逗号裁掉**，因此骨骼数值串的最后一个数值后面没有逗号。

> 每帧末尾的 `fn <帧号> ` 与后面那个逗号之间有一个空格（`fn 1234 ,`）；
> 带骨骼段数标记时是 `fn 1234 skeleton_42 ,`。
> 这个逗号是「帧头」与「骨骼数值串」的分界线，会在第 4 节的分包处理中被重新拼接。

## 2. 帧头字段

### 2.1 `<ActorName>` 演员名

| 项目     | 说明                                                                                                                                                                                 |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 出现条件 | 恒出现（字段本身总在，但通常是空串）                                                                                                                                                 |
| 来源     | `h2GloveStreamConfig::actorName`（`char[128]`，C 字符串）                                                                                                                        |
| 默认值   | 空串                                                                                                                                                                                 |
| 赋值途径 | 只有 `H2_SDK_setGloveStreamConfigBySN()` 会原样采用调用方传入的值；全局的 `H2_SDK_setGloveStreamConfig()` 刻意保留每台手套已有的名字、忽略传入值；配置文件里**没有**这一项 |
| 示例     | `Glove1`、`Actor01`                                                                                                                                                              |

它后面紧跟一个空格。它是**整帧的第一个 token**，`actorName` 为空时整帧**以空格开头**
（解析时要按 token 切分，不要假设第一个字符是可见字符）。
骨骼段数标记放在 `fn` 之后（见 2.9 节），因此这里不受影响。
CSV 录制文件名用的是另一条路径传入的演员名（`H2_SDK_startCSVRecord(actorName, …)`），
与本字段不联动。

### 2.2 `time <时间>`

| 项目     | 说明                                                  |
| -------- | ----------------------------------------------------- |
| 出现条件 | `timeEnable == 1`（默认 1；JSON 键 `timeEnable`） |
| 格式     | `YYYY-MM-DD HH:MM:SS.mmm`，**定长 23 字节**   |
| 时区     | 本机本地时间（`localtime`），不是 UTC               |
| 示例     | `time 2026-11-01 16:24:04.123`                      |

毫秒固定 3 位（`setw(3)` + `setfill('0')`），因此可以按固定位置解析，无需词法分析。
该时间戳来自系统墙钟，可能被 NTP 校时影响。

### 2.3 `pos`

| 项目     | 说明                                                         |
| -------- | ------------------------------------------------------------ |
| 出现条件 | `skeletonPosition == SkeletonPosition_Meter`（值 1，默认） |
| 含义     | 后续每段骨骼带 **3 个位置分量**，单位 **米**     |
| 不出现时 | `SkeletonPosition_None`（值 0）：帧中完全没有位置列        |

`pos` 本身不带数值，只是一个「之后有位置列」的标记。

### 2.4 姿态表示：`quat` 或 `euler <通道顺序>`

| 取值             | 出现条件                                                     | 含义                                                                          |
| ---------------- | ------------------------------------------------------------ | ----------------------------------------------------------------------------- |
| `quat`         | `skeletonAttitude == SkeletonAttitude_Quat`（值 2）        | 每段骨骼带 **4 个分量**，顺序 **W, X, Y, Z**，单位四元数          |
| `euler ZXY` 等 | `skeletonAttitude == SkeletonAttitude_Euler`（值 1，默认） | 每段骨骼带 **3 个分量**，单位 **度**，通道顺序由后一个 token 给出 |
| 都不出现         | `SkeletonAttitude_None`（值 0）                            | 帧中完全没有姿态列                                                            |

`euler` 后面**紧跟**一个通道顺序 token，可取值：

| token   | `channelOrder` | 旋转顺序                                 |
| ------- | ---------------- | ---------------------------------------- |
| `XYZ` | 0                | 先 X → 再 Y → 最后 Z                   |
| `XZY` | 1                | 先 X → 再 Z → 最后 Y                   |
| `YXZ` | 2                | 先 Y → 再 X → 最后 Z                   |
| `YZX` | 3                | 先 Y → 再 Z → 最后 X                   |
| `ZXY` | 4                | 先 Z → 再 X → 最后 Y（**默认**） |
| `ZYX` | 5                | 先 Z → 再 Y → 最后 X                   |

三个分量按该顺序给出，即 `ZXY` 下每段骨骼的三个数是 (Z 角, X 角, Y 角)。
**不要假设第一个数总是 X 轴角度。**

### 2.5 坐标系：`relative` 或 `global`

| token        | `skeletonCoordinate`                        | 含义                                     |
| ------------ | --------------------------------------------- | ---------------------------------------- |
| `relative` | `SkeletonCoordinate_Relative`（值 0，默认） | 旋转相对于**父骨骼**（局部坐标系） |
| `global`   | `SkeletonCoordinate_Global`（值 1）         | 旋转相对于**世界坐标系**           |

该枚举只有这两个有效值，所以两者必出现其一。

### 2.6 手势：`ges_l <左手势> ges_r <右手势>`

| 项目     | 说明                                                               |
| -------- | ------------------------------------------------------------------ |
| 出现条件 | `handGestureEnable == 1`（默认 0）                               |
| 取值     | 手势模板名，见下表                                                 |
| 未识别   | **空字符串**（此时文本形如 `ges_l  ges_r `，两个相邻空格） |

预置手势名（`gestureManager.cpp`，括号内为手势编号 index）：

| 名称     | index | 名称         | index  |
| -------- | ----- | ------------ | ------ |
| `1`    | 1     | `thumbUp`  | 8      |
| `2`    | 2     | `middleup` | 9      |
| `3`    | 3     | `ringup`   | 10     |
| `4`    | 4     | `pinkyup`  | 11     |
| `5`    | 5     | `rock`     | 12     |
| `ok`   | 6     | `grab`     | 13     |
| `daji` | 7     | （空串）     | 无匹配 |

判据是五指「第 1 指节与第 3 指节之间的角度差」是否落在模板区间内，
模板区间为开区间，阈值是经验值。

### 2.7 摇杆字段

整块只在 `joystickEnable == 1`（默认 0）时出现，顺序固定如下：

```
jsX_l <f> jsY_l <f> jsX_r <f> jsY_r <f>
jsDown_l <d> jsDown_r <d>
keyA_l <d> keyB_l <d> keyX_l <d> keyY_l <d> keyA_r <d> keyB_r <d> keyX_r <d> keyY_r <d>
thumbIndex_l <d> thumbMiddle_l <d> thumbRing_l <d> thumbPinky_l <d>
thumbIndex_r <d> thumbMiddle_r <d> thumbRing_r <d> thumbPinky_r <d>
```

| 字段                                              | 类型/格式                                                | 含义                                                          |
| ------------------------------------------------- | -------------------------------------------------------- | ------------------------------------------------------------- |
| `jsX_l` / `jsY_l`                             | 浮点，**固定 4 位小数**（`%1.4f`），范围 [-1, 1] | 左手摇杆水平/垂直量。X：最左 -1、最右 +1；Y：最上 -1、最下 +1 |
| `jsX_r` / `jsY_r`                             | 同上                                                     | 右手摇杆，**输出前对 X、Y 取反**，用于左右手坐标系镜像  |
| `jsDown_l/r`                                    | 整数 0/1                                                 | 摇杆按键按下                                                  |
| `keyA_*` / `keyB_*` / `keyX_*` / `keyY_*` | 整数 0/1                                                 | A/B/X/Y 按键按下                                              |
| `thumbIndex_*` … `thumbPinky_*`              | 整数 0/1                                                 | 拇指与食指/中指/无名指/小指接触（捏合）                       |

数值已按各自摇杆的校准中心/量程归一化并扣除死区，不是 16 位 ADC 原始值（原始值范围 0~65535）。
该侧没有摇杆硬件时相关字段仍会输出，取值为该侧数据结构的当前值（初始全 0）。

### 2.8 `fn <帧号>`

| 项目     | 说明                                                                                      |
| -------- | ----------------------------------------------------------------------------------------- |
| 出现条件 | 恒出现                                                                                    |
| 类型     | 无符号整数，十进制                                                                        |
| 起始     | **首帧为 1**，每生成一帧 +1，不回绕检查                                             |
| 复位     | 调用 `reset()` 后回到 1，接收端会看到帧号回退                                           |
| 关系     | 由流生成器自己维护，与 `libH2` 的算法计数器 `m_algCalcCounter` **不是**同一个量 |
| 分包     | 同一帧的所有分包共享同一个 `fn`                                                         |

接收端用它判断丢包与乱序。注意每台手套（每个 `libH2` 实例）有独立的帧号序列。

### 2.9 `skeleton_32` / `skeleton_42` / `skeleton_openxr`（规划中，尚未实现）

> **状态：需求已登记，当前 SDK 不会输出该字段。** 现有帧一律按 `skeleton_32` 解析。

**需求要点（已确认）**

1. 在 `fn <帧号>` **之后**增加 `skeleton_32` / `skeleton_42` / `skeleton_openxr` 三个取值之一
   （不放在整帧开头，以免破坏现有结构）；**没有该字段即为 `skeleton_32`**。
2. `skeleton_42` 按 `KHSL42_SkeletonIndex` 的定义顺序排列，**不是**把指尖追加到 32 段末尾。
3. `skeleton_42` 中 10 段指尖末端**同样输出角度**（不是只有位置），角度与其父骨骼（本指第 3 节）一致；
   `relative` 模式下"相对父骨骼的旋转填零"（单位旋转），但**这些列不能省略**；
   42 段的列数完全一致，不存在"只有位置"的段。

| 项目   | 说明                                                                   |
| ------ | ---------------------------------------------------------------------- |
| 位置   | **紧跟 `fn <帧号>` 之后**、分隔逗号之前（帧头最后一个 token）                          |
| 取值   | `skeleton_32`、`skeleton_42`、`skeleton_openxr` 三者之一，全小写 |
| 分隔   | 与前面的 `<帧号>`、后面的逗号之间各用**一个空格**分隔                  |
| 缺省   | **没有该字段即 `skeleton_32`**，与现有格式完全等价             |
| 重复性 | 属于帧头（在第一个逗号之前），因此**每个分包都会带上它**         |

三种取值的含义：

| 取值                | 骨骼段数                 | 每手                                   | 数值串组成                                                                                                                    |
| ------------------- | ------------------------ | -------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| `skeleton_32`     | 32                       | 16 = 手掌 + 5 指 × 3 节               | 见第 3 节                                                                                                                     |
| `skeleton_42`     | 42                       | 21 = 手掌 + 5 指 ×（3 节 + 指尖末端） | **按 `KHSL42_SkeletonIndex` 顺序排列**（见 3.3 节）；42 段**每段都有位置 + 姿态**，指尖末端的姿态与其父骨骼一致 |
| `skeleton_openxr` | 待定（规划 52，每手 26） | 26                                     | **待定**，布局确定前不得发送                                                                                            |

新接收端的解析顺序：

1. 在帧头里定位 `fn` 关键字，紧随其后的 token 是帧号；
2. 帧号后面若还有一个 `skeleton_32` / `skeleton_42` / `skeleton_openxr` token → 按它解释数值串布局；
3. 帧号后面直接就是分隔逗号（或 `subpackage i/N`）→ 该帧按 `skeleton_32` 处理（老格式）。

> 标记位置固定在 `fn` 之后，`<ActorName>` 不再需要任何约定或转义；老接收端照旧把第一个 token
> 当演员名也不受影响。

**兼容性要求（实现时必须遵守）**

- **42 段按 `KHSL42_SkeletonIndex` 的顺序排列**（右手 21 段 → 左手 21 段，指尖末端紧跟在本指第 3 节
  之后），**不追加到末尾**，详见 3.3 节。
- 由此带来一个必须承认的后果：`skeleton_42` 的数值串前 32 个"段"与 `skeleton_32` 的布局**不对应**
  （从第 5 个段开始就分叉：`skeleton_32` 的第 5 段是 `RHI1`，`skeleton_42` 的第 5 段是 `RHT3End`）。
  因此**老接收端不能再"只读前 32 段"**——它必须按首 token 识别 `skeleton_42` 并**整帧拒绝**，
  绝不能当成 32 段继续解析（那样不会报错，只会静默错位）。
- **指尖末端也有姿态**：42 段**全部**是"位置 + 姿态"，列数一致，可按固定步长解析。
  指尖末端的姿态在语义上**与其父骨骼（本指第 3 节）保持一致**，具体列值见 3.3 节的说明；
  数据源上没有独立传感器，实现时由父骨骼推导。
- **位置关闭时不发 42**：`pos` 未开启时整帧没有位置列，指尖末端更没有可输出的内容，
  此时一律按 `skeleton_32` 处理。
- **默认帧零变化**：这是老接收端兼容的主要保障——建议仅在骨骼数 ≠ 32 时才输出该字段，
  使默认配置下的帧与旧版逐字节一致。

**`skeleton_openxr` 待定项（实现前需要先定）**

- 具体骨骼数与顺序（规划：每手 26 个关节，双手 52）。
- OpenXR 关节带旋转，且含掌骨与腕骨，与现有 32 段不是一一对应；多出来的关节是否要带
  `quat` / `euler`、以及 `pos`/`quat` 标记如何扩展，需要另行约定。
- 在该布局写入本文档之前，**该取值不得出现在线上数据里**。

## 3. 骨骼数值串（逗号后的部分）

数值串的组成由两个维度决定：**骨骼段数**（`skeleton_32` / `skeleton_42`，见 2.9 节）与
**每段的列组成**（位置/姿态开关）。每段骨骼依次输出：位置 3 列（可选）→ 姿态 4 列或 3 列（可选）。

| `pos` | 姿态      | `skeleton_32` 每段列数 | `skeleton_32` 总数                     | `skeleton_42` 总数            |
| ------- | --------- | ------------------------ | ---------------------------------------- | ------------------------------- |
| 有      | `quat`  | 7                        | 224                                      | 294 = 42 × 7                   |
| 有      | `euler` | 6                        | 192                                      | 252 = 42 × 6                   |
| 有      | 无        | 3                        | 96                                       | 126 = 42 × 3                   |
| 无      | `quat`  | 4                        | 128                                      | 不支持，按 `skeleton_32` 处理 |
| 无      | `euler` | 3                        | 96                                       | 不支持，按 `skeleton_32` 处理 |
| 无      | 无        | 0                        | 0（**不产生任何分包**，见第 6 节） | 同左                            |

`skeleton_42` 的 42 段列数**完全一致**（每段 位置 3 列 + 姿态 4 或 3 列），只是**排列顺序与 32 段不同**
（见 3.3 节），因此接收端按固定步长即可顺序读取，不需要逐段判断列数。

`skeleton_openxr` 的列组成待定，见 2.9 节。

### 3.1 数值格式

| 数据     | 小数位                        | 说明                          |
| -------- | ----------------------------- | ----------------------------- |
| 位置     | 最多 6 位，**去尾随零** | 如 `0.0123`、`1.5`、`0` |
| 四元数   | 最多 6 位，**去尾随零** | 顺序 W, X, Y, Z               |
| 欧拉角   | 最多 3 位，**去尾随零** | 单位 度                       |
| 摇杆 X/Y | 固定 4 位                     | 不去尾零                      |

区间 `(-1e-6, 0]` 会被夹成 0，所以文本中不会出现 `-0` / `-0.000000`。
去尾零意味着**不要按固定字符宽度解析数值**，必须按逗号分隔取 token 再转浮点。

### 3.2 `skeleton_32` 的骨骼顺序

先右手 16 段，后左手 16 段，与固件协议一致（**调整该顺序会同时改变解码与上层语义**）：

| #  | 缩写      | 名称             |  | #  | 缩写      | 名称            |
| -- | --------- | ---------------- | - | -- | --------- | --------------- |
| 0  | `rHAND` | RightHand        |  | 16 | `lHAND` | LeftHand        |
| 1  | `RHT1`  | RightHandThumb1  |  | 17 | `LHT1`  | LeftHandThumb1  |
| 2  | `RHT2`  | RightHandThumb2  |  | 18 | `LHT2`  | LeftHandThumb2  |
| 3  | `RHT3`  | RightHandThumb3  |  | 19 | `LHT3`  | LeftHandThumb3  |
| 4  | `RHI1`  | RightHandIndex1  |  | 20 | `LHI1`  | LeftHandIndex1  |
| 5  | `RHI2`  | RightHandIndex2  |  | 21 | `LHI2`  | LeftHandIndex2  |
| 6  | `RHI3`  | RightHandIndex3  |  | 22 | `LHI3`  | LeftHandIndex3  |
| 7  | `RHM1`  | RightHandMiddle1 |  | 23 | `LHM1`  | LeftHandMiddle1 |
| 8  | `RHM2`  | RightHandMiddle2 |  | 24 | `LHM2`  | LeftHandMiddle2 |
| 9  | `RHM3`  | RightHandMiddle3 |  | 25 | `LHM3`  | LeftHandMiddle3 |
| 10 | `RHR1`  | RightHandRing1   |  | 26 | `LHR1`  | LeftHandRing1   |
| 11 | `RHR2`  | RightHandRing2   |  | 27 | `LHR2`  | LeftHandRing2   |

### 3.3 `skeleton_42` 的骨骼顺序（规划中，尚未实现）

`skeleton_42` 的数值串直接按 `KHSL42_SkeletonIndex` 的定义排列：**右手 21 段 → 左手 21 段**，
每根手指的指尖末端（`*End`）紧跟在该指第 3 节之后。**不是**把指尖追加到 32 段末尾。

| #  | 缩写        | 名称                | 列组成                                                                                           | 位置/姿态数据来源     |
| -- | ----------- | ------------------- | ------------------------------------------------------------------------------------------------ | --------------------- |
| 0  | `rHAND`   | RightHand           | 位置 3 + 姿态 4/3（均为解算值）                                                                  | 自身（32 #0）         |
| 1  | `RHT1`    | RightHandThumb1     | 位置 3 + 姿态 4/3（均为解算值）                                                                  | 自身（32 #1）         |
| 2  | `RHT2`    | RightHandThumb2     | 位置 3 + 姿态 4/3（均为解算值）                                                                  | 自身（32 #2）         |
| 3  | `RHT3`    | RightHandThumb3     | 位置 3 + 姿态 4/3（均为解算值）                                                                  | 自身（32 #3）         |
| 4  | `RHT3End` | RightHandThumb3End  | 位置 3（解算值）+ 姿态 4/3（`global`：同父骨骼；`relative`：零旋转 `1,0,0,0` / `0,0,0`） | 父骨骼 RHT3（32 #3）  |

读法说明：

- **"列组成"列**：42 段每段都是"位置 3 列 + 姿态列"（`quat` 4 列 W/X/Y/Z，`euler` 3 列），列数完全一致，
  接收端可按固定步长顺序读取。普通段的两部分都取自身的解算值；**10 个末梢的姿态按坐标系分两种情况填**：
  `global` 取父骨骼的姿态，`relative` 填零旋转（`1,0,0,0` / `0,0,0`）——两种情况都**占满**对应的 4 列或 3 列。
- **"位置/姿态数据来源"列**说明该段的位姿取自哪里：
  - **自身（32 #N）**：直接用 `skeleton_32` 的第 N 段——位置取 `handJointPosition32`，
    姿态取 `hand32RotQGlobal` / `handRotQLocal`；
  - **父骨骼 XXX（32 #N）**：10 个指尖末端没有独立传感器。位置取 `handJointPosition42` 的对应项，
    姿态**与其父骨骼（本指第 3 节）保持一致**。
- 姿态"与父骨骼一致"在两种坐标系下的落地方式不同，**实现时不要无脑复制父骨骼那一列的数**：
  - `global`：末梢的姿态就等于父骨骼的全局姿态，直接取父骨骼的列值；
  - `relative`：末梢**相对父骨骼的旋转填零**——`quat` 输出 `1,0,0,0`（W=1、XYZ=0，即"零旋转"的
    单位四元数，**不是**四个 0，四个 0 是非法四元数）；`euler` 按当前 `channelOrder` 输出三个 `0`。
    照抄父骨骼的相对旋转会让接收端在父链相乘后"多转一次"。
- **零值 ≠ 省略**：即使末梢的姿态恒为 `1,0,0,0` / `0,0,0`，这 4 列（或 3 列）**也必须照常输出**。
  省略会让整帧列数变少，按固定步长解析的接收端会从该点起全部错位。
- 判据：接收端用 `G_child = G_parent × Q_relative` 还原时，末梢的 `G` 必须等于父骨骼的 `G`。
- 由于 42 段顺序与 32 段不同，**第 5 个"段"就开始分叉**：`skeleton_32` 的第 5 段是 `RHI1`，
  `skeleton_42` 的第 5 段是 `RHT3End`。老接收端不能把 `skeleton_42` 当成 32 段解析。

## 4. 分包与 `subpackage i/N`

### 4.1 分包规则

| 项目       | 普通模式（`jumboFrameEnable == 0`，默认） | 巨型帧模式（`jumboFrameEnable == 1`）   |
| ---------- | ------------------------------------------- | ----------------------------------------- |
| 单包体上限 | 1400 - 128 = **1272 字节**            | **9216 字节**（9 KB，整帧一次发完） |
| 切分位置   | 只在**逗号处**切，绝不切断单个数值    | 同左                                      |

1400 是常见以太网 MTU 下的安全 UDP 载荷，128 预留给了包头与新增的 `subpackage` 前缀。
由于按「累计到下一个逗号」计算长度，单个分包可能**略微超过上限**（最多多出一个字段的长度），
这是刻意取舍：宁可包大一点也不能切坏字段。

### 4.2 每包的前缀

每个分包都以下面的形式开头：

```
<原帧头> subpackage <i>/<N>,<该包的数值串>
```

- `<原帧头>` 是原整帧中第一个逗号之前的全部内容（演员名 + 可选字段 + `fn <帧号>` + 可能缺省的
  `skeleton_*` 标记），因此**每个分包都自带骨骼段数标记**，可以独立解析；
- `i` 从 1 开始，`N` 为总包数；
- 前缀与数值串之间用逗号分隔，`subpackage` 之后的内容**属于帧头，不属于数值串**；
- 原帧头以空格结尾，拼接后又加一个前导空格，所以 `fn <帧号>` 与 `subpackage` 之间是**两个空格**。

**没有「未分包的裸帧」格式**：即使整帧只够打一个包，也会带上 `subpackage 1/1`。
调用方按 9 个分包预留了输出缓冲与长度数组。

### 4.3 传输顺序

`TxStdStringMsg(std::vector<std::string>)` 的发送顺序是「目标在外层、报文在内层」：
同一目标的各分包连续发出，便于接收端按到达顺序重组。

### 5.2 四元数 + 全局坐标系 + 手势 + 摇杆

配置：`skeletonPosition=1, skeletonAttitude=2, skeletonCoordinate=1, timeEnable=1, handGestureEnable=1, joystickEnable=1`，左手识别到 `ok`、右手未识别

Glove1 time 2026-11-01 16:24:04.123 pos quat global ges_l ok ges_r  jsX_l 0.0000 jsY_l 0.0000 jsX_r 0.0000 jsY_r 0.0000 jsDown_l 0 jsDown_r 0 keyA_l 0 keyB_l 0 keyX_l 0 keyY_l 0 keyA_r 0 keyB_r 0 keyX_r 0 keyY_r 0 thumbIndex_l 0 thumbMiddle_l 0 thumbRing_l 0 thumbPinky_l 0 thumbIndex_r 0 thumbMiddle_r 0 thumbRing_r 0 thumbPinky_r 0 fn 1235  subpackage 1/2,0.0123,0.0234,0.0345,1,0,0,0,…

注意 `ges_r` 后面是**两个空格**（右手术势名是空串），`fn 1235` 与 `subpackage` 之间也是两个空格。

### 5.3 同一帧的两个分包

```
Glove1 time 2026-11-01 16:24:04.123 pos quat global fn 1236  subpackage 1/2,0.0123,0.0234,…
Glove1 time 2026-11-01 16:24:04.123 pos quat global fn 1236  subpackage 2/2,0.0456,0.0678,…
```

两包的帧头完全相同（含同一个 `fn`），只有 `i/N` 与数值串不同。

### 5.4 `skeleton_42` 示例（规划中，当前不会产生）

```
Glove1 time 2026-11-01 16:24:04.123 pos quat global fn 1237 skeleton_42  subpackage 1/2,0.0123,0.0234,0.0345,1,0,0,0,…
Glove1 time 2026-11-01 16:24:04.123 pos quat global fn 1237 skeleton_42  subpackage 2/2,…,0.0812,0.0234,0.0456,1,0,0,0
```

- `fn 1237` 后面多了 `skeleton_42`（帧头最后一个 token），每个分包都有；
- 第一个 token 仍是演员名 `Glove1`，帧的整体结构不变；
- 数值串按 `KHSL42_SkeletonIndex` 顺序：右手 21 段 → 左手 21 段，指尖紧跟在各指第 3 节之后；
- `pos` + `quat` 时整帧 **294** 个数值 = 42 × 7（每段都有位置和姿态）；
- 前 4 段是 `rHAND`、`RHT1`、`RHT2`、`RHT3`（各 7 列）；**第 5 段是 `RHT3End` 的 7 列**
  （位置 + 与 `RHT3` 相同的姿态），第 6 段才是 `RHI1`——这就是与 `skeleton_32` 分叉的位置；
- 2/2 包末尾的 7 个数是 `LHP3End` 的 x/y/z 与 w/x/y/z；
- 若同一帧的坐标系是 `relative`，第 5 段（`RHT3End`）的 4 个姿态分量固定为 `1,0,0,0`
  （相对父骨骼的零旋转），前面 3 个位置分量仍是解算值——**这 7 列一个都不能少**。

## 6. 边界与已知限制

| 情况                                                                 | 实际行为                                                                                                                                                                           |
| -------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 整帧超过 9216 字节                                                   | 截断：写满时把游标压到末尾并清掉尾部字节，**后面的字段整段丢失**（骨骼按索引递增，越靠后的骨骼越先丢），帧仍然字符串闭合                                                     |
| 既不含位置也不含姿态（`skeletonPosition=0 && skeletonAttitude=0`） | 骨骼数值串为空，`splitFrame` 产生 0 个分包 → 该帧**既不上网也不写 CSV**                                                                                                   |
| `reset()` 被调用                                                   | 帧号回到 1，接收端会看到帧号回退，需要自行处理                                                                                                                                     |
| `getH2Stream()` 的输出缓冲                                         | 各分包**首尾相接、无分隔符**，必须按调用方拿到的长度数组切分，不能当 C 字符串拼接                                                                                            |
| 配置修改                                                             | `setStreamConfig()` 不下发、不加锁，只影响之后生成的帧；时间戳/位置/姿态/手势/摇杆等片段是**整段增删**而非留空占位，切换配置后列布局会变，接收端必须按帧头的标记字决定列数 |
| 欧拉角 + `relative` 与 `global`                                  | 两条分支传给转换器的四元数分量顺序不同（`relative` 直接传 WXYZ，`global` 先重排为 XYZW），这是既有实现；跨坐标系比对角度时不要假设两者可直接互相映射                           |
| 收到 `skeleton_openxr`                                             | 布局尚未定义，接收端应**整帧丢弃并记录告警**，不要按 32 或 42 猜测                                                                                                           |
| 收到未知的 `skeleton_*` 取值                                       | 同上，按未知布局丢弃；**不要**回退成 32 段继续解析                                                                                                                           |
| 老接收端收到 `skeleton_42`                                         | 必须**整帧拒绝**。当成 32 段解析不会报错，但第 5 段起全部错位                                                                                                                |
| `skeleton_42` 分包不齐                                             | 按 `i/N` 判断是否收全，缺包时整帧丢弃（分包按逗号边界切分，缺包无法局部还原）                                                                                                    |
| `skeleton_42` 列数不足（例如末梢把姿态列省掉了）                   | 列数是固定的 42×7（`quat`）或 42×6（`euler`），不足即视为帧损坏，整帧丢弃                                                                                                    |

帧长余量：9 KB 缓冲对 `skeleton_42` + `pos` + `quat`（294 个数值，约 2.9 KB）仍然宽裕；
但将来若采用 `skeleton_openxr`（规划 52 个关节且每个都带姿态，约 3.6 KB 量级）需要重新评估缓冲上限
与分包数（调用方按 9 个分包预留）。

## 8. CSV 录制与数据流的关系

CSV 录制写入的就是本文描述的同一份文本（`h2CsvRecordConfig::recordStream()`），
每帧一行、`\r\n` 结尾，因此**行内包含 `subpackage i/N` 前缀**；一帧被分成多个分包时，
这些分包的文本会**首尾相接地写在同一行**。

文件首行是表头，由同一份配置生成（如 `Time`、`Displacement(m):RightHand-X`、
`Quaternion:RightHand-W`、`Euler Angle(Degree):RightHand-X`），
骨骼列顺序与第 3 节一致，但表头**不包含**演员名、`subpackage`、`fn`、手势与摇杆字段。
也就是说表头列数与数据行的字段数并不相等，用表格软件直接打开会错列，
需要先按第 2 节的规则从行首剥掉帧头片段。

若将来启用 `skeleton_42`，CSV 侧需要同步处理（**尚未实现**）：

- 表头要按 `KHSL42_SkeletonIndex` 顺序重排，并为 10 个指尖末端补齐位置列
  （`Displacement(m):<名称>-X/Y/Z`）**和姿态列**（`Quaternion:<名称>-W/X/Y/Z` 或
  `Euler Angle(Degree):<名称>-X/Y/Z`），名称取 `kinemHumanSkeleton42`，否则列数与数据行对不上；
- CSV 行首同样会带 `skeleton_42` 标记（因为录制的是同一份文本），剥帧头时要一并处理。
